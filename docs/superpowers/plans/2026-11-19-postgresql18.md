# PostgreSQL 18 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Validate and adopt PostgreSQL 18 for InterMine CI, with a reproducible operator migration rehearsal.

**Architecture:** Fresh databases exercise current schema generation and integration suites. A separate PostgreSQL 14 fixture is logically restored into PostgreSQL 18 and compared before live application validation. Test services and volumes are task-owned.

**Tech Stack:** PostgreSQL 18.7 and 14, Java 8/21, Gradle 8.14.7, Docker, Python 3, existing JavaScript/Python clients.

**Spec:** `docs/superpowers/specs/2026-11-19-postgresql18-design.md`. User authorized the migration sequence and commit/push; implementation continues inline as in the preceding phase. The fresh design check found nothing important left.

## Global Constraints

- Preserve Java 8/21 compatibility during this PostgreSQL phase. The user approved Java 21 as the minimum for the next major release beginning with search modernization.
- Use SCRAM password authentication; no shared production databases or unrelated containers.
- Preserve logical table contents, sequence state, large objects and application ownership across fixture migration.
- PostgreSQL 18 Docker storage mounts at `/var/lib/postgresql`.
- Exercise existing real database suites; add regression tests only for actual new behavior/defects.

## Review Focus

- Fresh databases must permit the configured non-superuser application owner to create tables under PostgreSQL 18 defaults.
- Both mine and userprofile must be restored consistently; table-only counts must not hide sequence, large-object or row-content loss.
- Restore commands must fail on SQL errors and avoid overwriting a source database.
- Small-fixture query timings must not be presented as production benchmarks.
- PostgreSQL 18 client binaries must be used when backing up a PostgreSQL 18 server.
